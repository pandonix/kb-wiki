# AI 时代代码审查质量下降

## 核心现象

AI 编码工具普及后，PR（Pull Request）评审质量发生系统性下降：评审留言变多但更敷衍，大量 PR 无评审合并，线上故障上升，人均缺陷增加。^[raw/articles/2026-08-04-InfoQ-黑灯软件工厂失败.md]

## 实证数据

Faros AI 报告（AI 编码工具普及后的企业数据）：

- PR 评审留言数量**增加**，但质量下降——更多"LGTM"式敷衍
- 无评审合并的 PR 比例上升
- 线上故障数量上升
- 人均缺陷数增加

表面数据（评审留言数）可能误导——看起来"更多人在审查"，但实际上审查深度在下降。

## 三个根因

### 1. [[automation-bias]] — 信任 AI 代码

96% 的开发者不完全信任 AI 代码，但只有 48% 在提交前每次都检查。当 AI 生成的代码看起来"差不多"时，认知懒惰使人跳过深入审查。

### 2. PR 数量爆炸

AI 让代码生成速度远超人类，PR 数量成倍增加。但审查者的时间没有增加——每个 PR 的审查时间被摊薄，审查深度下降。

### 3. [[rlvr-architecture-blind-spot]] — 测试通过 ≠ 代码好

当 CI 全绿时，审查者容易默认"没问题"。但测试通过只验证功能，不验证架构、可维护性和设计质量。RLVR 的盲区在审查阶段被继承和放大。

## 审查质量下降的恶性循环

```
AI 生成代码速度↑ → PR 数量↑ → 每个 PR 审查时间↓ → 质量↓ → 低质量代码合并 →
线上故障↑ → 紧急修复消耗更多审查时间 → 审查能力进一步下降
```

## 对策

1. **分级审查**：高风险 PR（核心模块/架构变更）强制深度审查；低风险 PR（文案/配置）可快审
2. **30 分钟前置规划**：[[lights-out-software-factory]] 中的四步规划——先设计再编码，减少后续审查负担
3. **审查角色专门化**：将审查视为独立角色，而非"写完代码顺便看一眼"的附属行为
4. **不接受无审查合并**：零容忍，即使"看起来没问题"
