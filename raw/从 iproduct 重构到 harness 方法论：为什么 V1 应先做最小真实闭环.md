# 从 iproduct 重构到 harness 方法论：为什么 V1 应先做最小真实闭环

今天关于 i product 重构，沉淀出两条经验：

1. **AI 时代，面对历史包袱重、路径依赖强、局部修补成本持续升高的旧项目时，重构往往比修补更合理。**
2. **AI 让重构变便宜了，但没有让协同复杂度变便宜；因此 V1 应优先串行闭环，不要过早并行。**

如果再用 harness 的方法论来看，这两条经验其实还能进一步收敛成一套更硬的工程判断。

## 一、重构不只是重写代码，而是重建运行骨架

在 harness 视角里，一个系统是否值得继续修补，不只看代码脏不脏，而看这些基础骨架是否已经失效：

- 任务入口是否清晰
- 状态和上下文是否可组织
- 边界是否明确
- 失败后是否可定位、可恢复
- 结果是否可验证
- 系统是否适合持续迭代优化

如果这些骨架已经坏了，那么继续 patch，本质上是在一个失去可控性的系统上继续补洞。短期看像是在推进，长期看只会让系统更难验证、更难调试、更难演进。

所以，AI 时代的“重构”不应理解成“重写一遍”，而应理解成：

> **重新建立任务流、状态流、验证流和恢复流。**

换句话说，重构的目标不是“代码更优雅”，而是重新拿回系统的**可运行性、可验证性与可控性**。

## 二、V1 串行优先，本质上是在保护最小真实闭环

harness 方法论天然反对一开始就堆复杂编排。

在最小链路还没跑稳时，过早进入多 worktree、多 contract、多角色、多前后端并行，问题会迅速变成：

- 是任务切分错了？
- 是 contract 不稳？
- 是上下文没传对？
- 是 mock 和 placeholder 混进主链路了？
- 是状态不同步？
- 是哪一段协作结果污染了主路径？

这时团队表面上在开发，实际上大量时间都花在 debug 协同复杂度。

所以更稳妥的顺序是：

> **先做 single-threaded truth path，再做 parallel orchestration。**

也就是：

- 先有一条真实、端到端、可反复通过的主路径
- 再考虑把其中部分环节拆开并行
- 否则并行只会放大噪音与不稳定性

这也是为什么 V1 更应优先：

- 最小 contract
- 真实联调
- 主路径闭环
- 串行推进

而不是一开始就追求多线并行和漂亮分层。

## 三、前端应后置，CLI / harness 应前置

如果系统仍处于快速变化阶段，那么正式前端通常不是最好的验证工具。

更合适的顺序往往是：

> **DB → backend → CLI / test harness → frontend**

原因不是单纯“CLI 更快”，而是它更接近真相：

- 更容易暴露真实输入输出
- 更容易验证状态迁移
- 更容易写测试
- 更容易回放和定位问题
- 不容易被 UI 复杂度掩盖核心逻辑问题

所以从 harness 角度看：

> **前端不是验证系统成立性的最好工具；最小可验证 harness 才是。**

正式前端适合消费稳定性，不适合制造稳定性。

## 四、mock / placeholder 可以有，但必须被严格隔离

这次重构的一个典型问题，是前端 placeholder、后端 mock、临时实现和未稳定 contract 混在一起，最后在合并阶段集中爆炸。

harness 方法论对此非常敏感，因为它要求严格区分：

- 哪些是 production path
- 哪些是 test fixture
- 哪些是临时 stub
- 哪些是 simulation layer

所以需要明确几条纪律：

1. **mock 可以有，但必须显式标注、显式隔离**
2. **placeholder 不能默认混入主路径**
3. **主路径必须定期在真实依赖上跑通**
4. **所有临时层都要有退出标准和清理时机**

重点不是禁止假数据，而是防止：

> **假的链路看起来像真的闭环。**

## 五、重构优先级应放在 contract、状态机和验证方式上，而不是 UI 表层

很多团队说重构，最后做成了：

- 换技术栈
- 重写页面
- 改目录结构
- 替换组件

但 harness 视角会先问：

- 最小输入是什么？
- 最小输出是什么？
- 成功标准是什么？
- 失败类型是什么？
- 中间状态有哪些？
- 哪些节点能 checkpoint？
- 哪些环节能自动验证？
- 哪些判断必须保留人工介入？

所以真正优先重构的，不是表层页面，而是：

- contract
- 状态机
- 任务边界
- 验证方式
- 失败恢复机制

这也解释了为什么前端应该后置。

## 六、V1 先追求行为可信，不要过早追求结构炫技

重构项目常见误区是：

- 一开始就想把架构分层做得很漂亮
- 边界切得很工整
- service / repo / worktree 拆得很高级

但行为还没稳定，结构先复杂了。

harness 的偏好刚好相反。它优先问的是：

- 这条路径能不能稳定完成任务？
- 能不能被评测？
- 能不能复跑？
- 出错后能不能快速定位？
- 能不能基于结果做下一轮优化？

因此，V1 最重要的不是“架构美感”，而是：

> **行为可信、链路真实、验证明确、失败可恢复。**

## 七、把这两条经验翻译成 harness 版原则

最后可以把今天的经验收敛成 6 条原则：

1. **先重建可运行骨架，再修补表面功能**
2. **先跑通单线程真实主路径，再做并行协作**
3. **先定义最小 contract，再扩展模块边界**
4. **先用 CLI / test harness 验证系统，再上正式前端**
5. **mock / placeholder 必须显式隔离，不能混入主路径**
6. **V1 先追求行为可信，再追求结构优雅**

## 八、一句话结论

> **AI 时代的重构，不该理解成“重写一遍代码”，而应理解成“重新建立一个最小、真实、可验证、可恢复的生产 harness”；而 V1 串行优先，本质上就是先保护这个 harness 的稳定性。**
