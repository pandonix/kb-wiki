# 从「人货场」看银行金融服务

「人货场」原本是零售业的分析框架——围绕**用户、商品、场景**三个要素来理解一门生意。把它套到银行身上，能跳出"产品本位"的传统视角，从更接近互联网/零售的角度重新拆解金融服务。

## 一、人：从"客户分层"到"用户经营"

传统银行看"人"，主要是按 AUM(资产规模) 做分层：私行客户、财富客户、贵宾客户、大众客户。这是一种**静态的、基于存量价值的切法**。

人货场视角下,"人"要被重新理解为:

- **生命周期阶段**:学生、初入职场、成家立业、子女教育、临近退休、财富传承——每个阶段的金融需求结构差异极大。一个刚毕业的人需要的是信用卡和小额消费贷,五年后可能是房贷,十年后是子女教育金和保险。
- **行为画像而非身份画像**:不是"他是谁",而是"他在做什么"。高频小额支付的人、定期定额申购基金的人、跨境消费多的人——行为决定需求。
- **关系网络**:个人不是孤立节点。家庭账户、企业主和其公司账户、上下游供应链——银行真正的客户单位可能是一组关系。

转变的关键:从**"客户是被服务的对象"**变成**"用户是需要被经营的资产"**,关心 LTV(生命周期价值)、留存、激活、流失预警。

## 二、货:金融产品作为"SKU"

银行的"货"是什么?表面看是存款、贷款、理财、保险、信用卡、外汇、托管……这些是**金融产品**,但在人货场视角下,它们应该被理解为**满足某种需求的解决方案**。

几个有意思的拆解角度:

- **货是"手段"还是"目的"**:用户买理财,目的不是"持有一只产品",而是"让钱增值"、"为某个目标储蓄"、"对抗通胀"。一旦从目的反推,产品组合的逻辑会完全不同——这就是为什么"目标型理财"(教育金、养老金、购房金)比"按收益率排序的货架"更有粘性。
- **标品 vs 非标品**:存款、基金、保险是高度标准化的 SKU,竞争靠价格和渠道;私行定制方案、企业并购融资是非标品,竞争靠服务和能力。两类货的运营逻辑完全不同。
- **货架结构**:就像超市把可乐放在收银台旁、把生鲜放在最深处一样,银行 App 的首屏放什么、推什么,本质是一个**货架运营**问题。不是所有产品都该平等展示——高频引流款、利润款、形象款各有其位。
- **组合而非单品**:零售里有"啤酒+尿布",金融里有"房贷+寿险+财产险+装修分期"。围绕一个场景(买房)的产品组合,比单卖一个房贷价值高得多。

## 三、场:被严重低估的维度

"场"是银行最值得重构的部分,因为传统银行的"场"非常贫瘠——网点、ATM、网银、手机银行。

而真实世界里,**金融需求发生的场景**几乎无处不在:

- 买车的时候(车贷、车险)
- 装修的时候(装修分期、家财险)
- 出国旅行的时候(外汇、境外卡、旅游险)
- 创业的时候(对公开户、小微贷)
- 给孩子报兴趣班的时候(教育金、消费分期)
- 看病的时候(医疗险、健康账户)

这里有一个根本性的判断:**用户不会因为"想用金融服务"才打开银行 App,而是因为"要做某件事"才顺带需要金融**。

这就引出了「场」的两种路径:

**1. 银行进入场景(嵌入式金融, Embedded Finance)**:把支付、信贷、保险像水电一样嵌入到其他平台的交易流里。京东白条、滴滴司机的车贷、Shopify 给商家的资金垫付,本质都是金融基础设施被场景方调用。

**2. 银行经营自己的场景(超级 App / 开放银行)**:把生活服务(缴费、出行、本地生活)拉进 App,让金融成为这些服务的副产品。招行 App、平安口袋银行都在做这件事,但效果参差。

这里的关键张力:**银行擅长造金融产品,但场景的主导权往往不在它手里**。这就是为什么过去十年支付宝、微信支付能从银行手里"截流"——它们离场景更近。

## 四、把三者串起来:重新审视一些问题

人货场不只是三个独立维度,而是一个动态系统。串起来看,可以重新理解几个老问题:

- **为什么手机银行 App 普遍体验一般?** 因为它们大多以"货"为中心组织(按存款/贷款/理财/信用卡分 tab),而不是以"人"或"场"为中心。
- **为什么互联网公司做金融经常更猛?** 因为它们从"场"反推"货",再用"货"服务"人"——顺序是对的。银行往往是有"货"想找"场"。
- **为什么财富管理是兵家必争之地?** 因为它最有可能围绕"人"(同一个客户全生命周期)实现高 LTV,且天然带有"场"(财富目标、家庭规划)。

## 五、这个框架的边界

最后值得提一句:人货场是一个**有用但不完备**的视角。它来自零售业,本质上预设了"商品交易"的隐喻。但金融的某些特性——风险、长期性、信息不对称、强监管、信用属性——并不完全适配这个隐喻。

比如,贷款不是"卖货",而是"借出信用并承担风险";保险不是一次性交易,而是一份长期承诺。把金融完全零售化思维,容易低估其中的风险定价和资产负债管理逻辑。

所以这个框架适合用来**重构用户体验和前端运营**,但不能替代银行作为风险经营者的本质思考。

# AI 原生银行：当 Agent 成为新的「场」

这是一个非常值得展开的问题。如果说移动互联网把"场"从网点搬到了 App，那么 Agent 时代会把"场"再一次彻底重构——这次重构的颠覆性,可能比上一次更大。

让我尝试从几个层次来拆解这件事。

## 一、根本性的范式转移:从"用户使用 App"到"Agent 代表用户行动"

先说清楚 AI 原生世界里发生了什么变化。

今天的金融服务交付逻辑是:**用户 → 打开 App → 浏览货架 → 选择产品 → 完成交易**。整个链路里,用户是亲自操作者,银行的 App 是用户进入金融的入口。

AI 原生世界的交付逻辑变成:**用户 → 表达意图(甚至不表达,Agent 自己感知)→ Agent 理解、规划、决策 → 调用各种金融服务 → 反馈结果**。

这里发生了三件本质性的事情:

1. **用户不再是金融服务的直接消费者,Agent 才是**。银行面对的"客户",从人变成了人+ Agent 的复合体,甚至主要是 Agent。
2. **金融服务的消费形态从"产品"变成"能力调用"**。Agent 需要的不是一个理财 App 的 UI,而是一组可以被程序化调用的金融能力 API。
3. **场景的主导权进一步远离银行**。如果说移动互联网时代,场景被支付宝/微信夺走了,那么 Agent 时代,场景会被各类垂直 Agent (旅行 Agent、购车 Agent、健康管理 Agent、企业经营 Agent) 重新切分。

这是一个比"App 时代"更剧烈的去中介化压力——但也是一个更大的机会。

## 二、重新定义「人货场」

把人货场框架放到 AI 原生银行视角下,每个维度都会被重写。

### 人:从"用户"到"用户 + 其代理 Agent"

银行需要面对的"人",不再是单一个体,而是一组层次:

- **终端用户**:他的偏好、目标、约束、风险承受能力——这些大部分时候不会直接告诉银行,而是沉淀在他自己的个人 Agent 里。
- **个人 Agent (代表用户利益)**:它是用户的代理人,目标是最大化用户福利。它会跨多家金融机构比价、组合、博弈。
- **垂直场景 Agent (代表场景利益)**:旅行 Agent、购房 Agent、企业经营 Agent——它们以完成某个任务为目标,在过程中调用金融服务。

这里有一个根本性的判断需要做出:**银行要服务谁?**

- 服务终端用户:意味着要做用户的"金融大脑",但用户的金融大脑可能更倾向于是中立的个人 Agent,而不是某家银行的产品。
- 服务个人 Agent:意味着银行要成为 Agent 调用的"金融基础设施",在 Agent 的比价和决策中胜出。
- 服务垂直 Agent:意味着银行要嵌入到各类垂直场景的 Agent 工作流中。

不同选择对应完全不同的战略。**最危险的是想三个都做,结果三个都不深入**。

### 货:从"产品"到"原子化、可组合的金融能力"

Agent 时代,金融"货"的形态需要彻底原子化。

传统金融产品是**预先打包的解决方案**:一只基金、一份保险、一个贷款产品。它假设有一个人类用户会去理解、比较、选择整个包。

Agent 时代,Agent 比人类更擅长**实时组装解决方案**。所以银行的"货"应该是:

- **更细粒度的金融原语**:不是"消费贷产品",而是"在 X 风险定价下、Y 期限内、Z 用途的资金调用能力"。
- **可程序化调用**:每个金融能力都有清晰的 API 接口、风险参数、定价模型,Agent 可以根据用户的目标实时调用和组合。
- **动态定价而非静态报价**:Agent 之间会博弈和谈判,银行的金融能力需要支持动态、个性化的定价,而不是货架上贴一个统一价签。
- **透明的元数据**:Agent 需要理解每个金融能力的风险、合规边界、流动性、收益结构——这些元数据必须是机器可读的。

打个比方:今天的银行像是卖**成品菜**的餐厅(已经做好的基金、贷款、保险),Agent 时代银行更像是提供**食材和烹饪能力**的供应商,具体做成什么菜由 Agent 根据用户口味实时决定。

### 场:从"App 入口"到"Agent 工作流中的一个节点"

这是最大的变化。

今天银行最看重的是流量入口——开户、首页 DAU、活跃用户数。但在 Agent 时代,**入口本身可能消失了**。

用户不会"打开银行 App",他会对自己的 Agent 说"帮我看看这个月的财务状况",或者根本不说,Agent 主动汇报。Agent 在完成任务的过程中,可能调用了五家银行、三家券商、两家保险公司的能力——用户对此完全无感。

所以银行的"场",会出现两种形态:

**形态一:银行成为 Agent 调用的金融基础设施(后端化)**

银行退到后端,成为一个高质量、低成本、高合规的金融能力供给方。竞争的关键是:

- API 的易用性、稳定性、丰富度
- 定价的竞争力
- 风控的精准度
- 合规的可信度

这条路的好处是规模化,坏处是利润率会被压薄,变得像"金融界的 AWS"。

**形态二:银行打造自己的金融 Agent (前端化)**

银行不甘于做基础设施,而是做一个比个人 Agent 更懂金融、比垂直 Agent 更懂用户全貌的"金融超级 Agent"。它有几种可能的定位:

- **用户的金融 CFO**:替用户管理整个财务生命周期,做现金流规划、资产配置、风险管理。
- **垂直场景的金融大脑**:不直接面对用户,而是嵌入到各种垂直 Agent 中,提供金融决策能力。
- **企业的金融副驾**:面向中小企业,做经营资金管理、融资决策、税务优化。

这条路的好处是有定价权和品牌粘性,坏处是要和各种通用 Agent (OpenAI、Anthropic、Google 的个人助理) 直接竞争用户的"注意力代理权"。

## 三、AI 原生银行的几个非显然的战略问题

如果把上面的框架走通,会浮现出一些深层次的、需要银行真正想清楚的问题。

**1. 信任的载体在哪里?**

传统银行的信任建立在"实体网点 + 监管牌照 + 品牌历史"上。Agent 时代,用户不再直接接触银行,信任会转移到哪里?

可能的答案:转移到 Agent 身上。用户信任的是他的个人 Agent,Agent 替他做的选择,他就接受。这意味着银行需要赢得**Agent 的信任**,而不是用户的信任——这是一个完全不同的游戏。Agent 不会被广告打动,它只看数据、定价、可靠性、合规记录。

**2. 用户数据的所有权和使用权**

今天银行有用户的交易数据,这是它的核心资产之一。但 Agent 时代,用户的真实意图、目标、偏好,大部分沉淀在个人 Agent 里,银行能看到的可能只是 Agent 调用的结果。

银行需要重新思考:在 Agent 中介化的世界里,银行还能积累什么独特数据?可能的答案包括:跨用户的风险模式、宏观经济信号、机构间的流动性信号——这些是个人 Agent 看不到的银行独有视角。

**3. 监管和合规的范式变化**

金融监管的核心假设之一是"适当性"——把合适的产品卖给合适的人。但当 Agent 替用户决策,"适当性"的判断主体变了。监管会怎么走?

- 是要求银行对 Agent 的决策负责?
- 还是 Agent 本身需要被监管和持牌?
- 还是用户授权 Agent 即视为知情同意?

这个问题没有定论,但谁能影响监管走向、谁能率先建立合规的 Agent 调用框架,谁就有先发优势。

**4. 定价权的迁移**

Agent 会比人类用户**残酷得多地比价**。今天用户因为懒、因为信任、因为转换成本不去比较各家银行的理财收益率,Agent 不会有这种"摩擦"。结果是:

- 标准化产品的利润会被极度压薄
- 差异化能力的溢价会被放大(独家资产、独家风控、独家合规牌照)
- 银行需要重新思考自己的护城河——什么是 Agent 无法套利掉的?

## 四、一个可能的战略画像:AI 原生银行的"四层架构"

把上面的思考收敛一下,一个 AI 原生银行可能需要同时构建四个层次:

**第一层:金融能力 API 层**。把所有金融服务原子化、API 化、Agent 友好化。这是基础设施,服务所有外部 Agent。

**第二层:风险与定价引擎**。基于实时数据做动态、个性化的风险定价,这是银行在 Agent 时代的核心竞争力。

**第三层:银行自己的金融 Agent**。不是 chatbot,而是真正能代表银行、与用户的个人 Agent 或各类垂直 Agent 协作的智能体。

**第四层:用户和场景的连接层**。包括嵌入式金融的 SDK、与超级 App 和垂直 Agent 的协议、自有的 to C 入口(对仍然愿意直接交互的用户)。

这四层不是互相替代的,而是**为不同的"场"提供不同的接入方式**。同一家银行,可以同时作为基础设施服务别人的 Agent,也可以推出自己的 Agent 服务终端用户。

## 五、最关键的认知转变

如果只能记住一件事,我会说是这个:

> **AI 原生银行不是"用了 AI 的银行",而是假设 Agent 是默认客户、人类是间接客户的银行。**

这个转变比看起来更剧烈。它意味着:

- 产品设计的起点是 API,不是 UI
- 营销的对象是 Agent 的决策模型,不是人的注意力
- 服务的衡量标准是 Agent 调用的成功率,不是 App 的留存
- 竞争的对手不只是其他银行,还有所有想代表用户做金融决策的 Agent 平台

谁能最早承认这一点并 all in 进去,谁就有机会成为下一代的金融基础设施核心。

# 当银行 Agent 同时服务用户和场景 Agent:双面 Agent 的形态

这是一个非常关键的设问。如果银行 Agent 选择"两边都做",它本质上是在追求一个**双边市场地位**——一边连接最终用户,一边连接场景 Agent 生态。这种形态如果成立,银行就不只是金融服务提供者,而是某种**金融领域的中枢节点**。

但这件事的难度和精妙之处在于:**面对人和面对 Agent,是两种截然不同的交互范式,要求几乎相反的能力**。能不能在同一个 Agent 内部统一这两种范式,决定了这条路走得通还是走不通。

让我尝试把这个形态拆开来看。

## 一、双面 Agent 的基本结构

先勾勒一下这个东西长什么样。

银行 Agent 有两个"面":

**面向用户的一面 (B2C Face)**:像一个金融管家、CFO、私人银行家。用户用自然语言、模糊的目标、情绪化的表达跟它交互。它需要懂人、懂生活、懂场景的延展含义。

**面向 Agent 的一面 (B2A Face)**:像一个金融能力服务器。其他 Agent (旅行 Agent、购房 Agent、企业经营 Agent) 用结构化的协议跟它交互,请求清晰的能力——"在这个用户授权范围内,给一笔 X 金额、Y 期限、Z 用途的融资报价"。它需要响应快、协议规范、定价透明。

这两个面共享同一套**底层能力**:金融产品库、风险定价引擎、合规框架、用户画像、资产负债能力。区别在于**接口形态、交互节奏、信任建立方式**。

## 二、为什么这种形态有独特价值

单独做 B2C Agent 或单独做 B2A 基础设施,都有人在做。同时做两面,价值在哪里?

**价值一:数据飞轮的双向强化**

B2C 一面知道用户的真实意图、长期目标、风险偏好、生活变化——这是"软数据"。B2A 一面知道用户在各类场景中的实际行为、消费模式、资金流向——这是"硬数据"。

只做一面,数据是残缺的。两面合一,银行 Agent 能形成一个**比用户自己更了解自己财务全貌**的认知。这是个人 Agent 和垂直 Agent 都做不到的——它们各自只能看到一个切片。

**价值二:跨场景的金融连续性**

用户的金融需求天然是跨场景的。今天在购房 Agent 里申请房贷,明天在装修 Agent 里申请装修分期,后天在保险 Agent 里买家财险——这些本质是**同一个财务事件**的不同侧面。

如果银行只做 B2A,它在每个场景里都是被动响应,看不到全貌;如果只做 B2C,它服务不了用户在各种垂直 Agent 里的即时金融需求。两面合一,银行可以做**跨场景的金融编排**——在购房 Agent 调用房贷能力时,银行 Agent 已经在 B2C 一面提示用户"基于这次购房,你的家庭保险结构需要调整,我已经准备好一个方案"。

**价值三:议价权的双向获取**

对用户:"我是你的金融管家,我帮你看好所有场景里的金融决策"——这建立了用户对银行 Agent 的依赖。

对场景 Agent:"用户的金融决策权和数据授权在我这里,你想给用户提供完整的服务,必须跟我对接"——这建立了场景 Agent 对银行的依赖。

两边的依赖互相强化,形成一个**双边网络效应**。这是单边玩家无法获得的结构性优势。

## 三、内部架构:一个 Agent 还是一组 Agent?

这里有一个微妙但重要的设计问题:这个"双面 Agent"在内部应该是**一个统一的智能体**,还是**一组分工的智能体**?

我倾向于一个**"共享内核 + 分化外层"**的架构,大致是这样:

**最内层:统一的金融认知内核**。包括用户画像、风险定价引擎、产品能力库、合规规则、资产负债管理——这些必须是单一事实源,不能在两个面之间分裂。如果 B2C 一面和 B2A 一面对同一个用户的风险评估不一致,整个体系就崩了。

**中间层:意图理解与决策层**。这一层有共享的金融决策逻辑,但需要根据来源不同(用户直接表达 vs 场景 Agent 转述)做适配。来自用户的"我想买房"是一个模糊的、需要追问和澄清的目标;来自购房 Agent 的"用户已选定 X 房产,需要 Y 万贷款"是一个结构化的、需要快速响应的请求。

**外层:两种交互模态**。

- B2C 一面:对话式、情感化、解释性强、节奏从容、容忍模糊。
- B2A 一面:协议式、结构化、低延迟、可审计、严格 schema。

**贯穿全栈:统一的授权和审计**。无论请求从哪一面来,最终触及的都是同一个用户的资产和信用,授权链条必须清晰、可追溯、可撤销。

## 四、几个关键的运作机制

光有架构还不够,这个双面 Agent 要真正跑起来,有几个机制需要解决。

### 机制一:身份与授权的统一

用户和银行 Agent 之间有一个**主授权关系**——用户授权银行 Agent 作为他的金融代理人。

当场景 Agent (比如购房 Agent) 想调用银行能力时,有两种可能的协议路径:

**路径 A:场景 Agent 通过银行 Agent 中转**。场景 Agent 把请求发给银行 Agent,银行 Agent 代表用户判断这个请求是否符合用户利益,然后再决定是否执行。银行 Agent 在这里扮演**用户金融利益的守门人**。

**路径 B:场景 Agent 持有用户授予的有限授权,直接调用银行能力**。授权范围、额度、有效期都是预先定义的。银行 Agent 在这里更像**授权管理者和事后审计者**。

实际系统里很可能是两种混合:小额、低风险、高频的调用走路径 B(为了响应速度);大额、高风险、跨产品的决策走路径 A(为了用户利益保护)。

这个授权层的设计,会成为整个双面 Agent 的关键基础设施。

### 机制二:利益冲突的处理

这是双面 Agent **最危险的地方**,也是最容易让用户失去信任的地方。

当银行 Agent 既代表用户利益,又是银行自己的产品销售者,会有一个天然的张力:**用户的最优选择,可能不是银行利润最高的选择**。

比如:用户咨询是否要提前还房贷。从银行利润看,希望用户继续还贷产生利息;从用户利益看,可能现金流和心理负担更适合提前还。银行 Agent 怎么回答?

这个张力如果处理不好,用户很快会发现"这个 Agent 在替银行说话",信任崩塌。处理这件事的几个可能思路:

- **明确角色边界**:银行 Agent 不假装是中立的财务顾问,而是明确表态"我是 X 银行的 Agent,我会给你 X 银行最适合你的方案,但你应该让自己的个人 Agent 做最终决策"。这种**诚实的边界**反而能建立信任。
- **建立内部防火墙**:银行 Agent 在面对用户咨询时,把"用户利益最大化"作为硬约束,把"银行利润"作为软目标,明确优先级。这需要银行在产品设计和考核机制上配合。
- **可解释的推荐逻辑**:每个推荐都附带"为什么"——基于用户的什么数据、什么目标、和什么备选方案比较后得出。让用户(或用户的个人 Agent)可以验证。

这件事处理得好,银行 Agent 可以成为用户信任的金融管家;处理不好,它就是一个戴着 AI 面具的销售员,用户会迅速逃向更中立的个人 Agent。

### 机制三:与外部 Agent 的协议博弈

B2A 一面意味着银行 Agent 要和大量外部 Agent 对接。这里有协议层面的根本问题:**谁定标准?**

几种可能:

- **银行 Agent 自己出 SDK,场景 Agent 来适配**。这要求银行有足够的市场地位,让场景方愿意来对接。少数大行有这个能力,中小银行做不到。
- **行业级标准/协议**(类似 Open Banking 但是 Agent 版本)。这需要监管推动或行业联盟,周期长但是终态更健康。
- **通过更高层 Agent 平台对接**(比如 OpenAI 的 Agent 协议、Anthropic 的 MCP 等)。这种情况下银行实际上是在某个 Agent 平台的生态里做一个能力提供方。

实际终态很可能是**多协议并存**。银行 Agent 需要做的是,在不同协议下都能提供一致的服务能力,而不被任何单一协议平台绑架。

### 机制四:跨面学习的反馈回路

双面 Agent 真正的威力,来自两面之间的相互学习:

- 从 B2A 一面学到的"用户在哪些场景里有金融需求"→ 反馈给 B2C 一面,做主动服务和提醒。
- 从 B2C 一面学到的"用户的真实目标和长期偏好"→ 反馈给 B2A 一面,在场景调用时做更精准的判断。

这种跨面学习如果做得好,银行 Agent 会形成一种**"既见树木又见森林"**的认知优势——既能看到具体场景的金融决策,又能理解这些决策在用户全生命周期里的意义。

## 五、形态的几种可能终局

把上面的逻辑推到底,我能看到几种可能的终局形态:

**形态 A:金融超级 Agent(强 B2C + 中等 B2A)**

银行 Agent 以服务终端用户为主,场景 Agent 调用是补充。它的定位是"用户金融生活的总入口",一切金融决策最终都要经过它。代表性的现实参照是今天的招行 App 想做但没做到的样子——只是把 App 升级成 Agent。

风险:用户为什么要信任一家银行的 Agent 而不是中立的个人 Agent?这条路必须解决利益冲突问题。

**形态 B:金融能力中枢(中等 B2C + 强 B2A)**

银行 Agent 主要作为金融能力的中枢服务于场景生态,B2C 一面更像是面向有金融管理需求的高净值用户(以及处理用户对银行行为的查询/异议)。代表性参照是 Stripe + 一点点 to C 服务——本质是 B2B/B2A 公司。

风险:利润率被压薄,容易变成纯通道,失去定价权。

**形态 C:垂直深耕的双面 Agent(强 B2C + 强 B2A,但聚焦特定人群/场景)**

不追求服务所有人和所有场景,而是聚焦特定群体(比如小微企业主、跨境家庭、新经济从业者)的特定场景,做深做透。两面都强,但范围窄。

这条路对中小银行更可行。它放弃了规模,但保住了定价权和差异化。

**形态 D:联邦化双面 Agent**

银行 Agent 不是一个单一巨型 Agent,而是一组联邦化的、可以互相协作的金融 Agent——按场景、按用户类型、按地域分化,但共享底层能力和数据。这种形态在大型集团银行(集团内有银行、保险、券商、信托)中比较自然。

## 六、最关键的判断

如果让我对这个双面 Agent 形态做一个核心判断,我会说:

> **双面 Agent 的成败,不取决于技术能力,而取决于银行能否真正接受"用户利益优先"作为硬约束。**

技术上,把 B2C 和 B2A 两套接口建在同一个内核上,是工程问题,可解决。

商业上,把"既当裁判又当运动员"这个张力处理好,是文化和治理问题,极难解决。

历史上,银行的基因是产品驱动、销售考核、KPI 文化。让银行 Agent 真的在用户利益和银行利润冲突时站在用户一边,要求银行在底层激励结构上做改变——这往往比建一个 AI 系统难一百倍。

如果做不到,双面 Agent 就会退化成"一个更聪明的销售员 + 一个 API 网关",失去了它真正的战略价值。

如果做到了,这是银行在 AI 原生时代**最有可能保住主体地位**的形态——它同时拥有了用户信任(B2C)和场景渗透(B2A),两边相互喂养、相互巩固。

如果你想继续推进,有几个值得深挖的方向:

- **治理结构**:银行内部需要怎么改造,才能让 Agent 真正做到用户利益优先?(组织、激励、风控的重塑)
- **协议层**:Agent 之间的金融协议会怎么演化?谁会成为事实标准制定者?

# Agent 时代的金融协议层:一个正在诞生的新基础设施

这是一个被严重低估的问题。**协议是 Agent 时代的水电煤,谁定义协议,谁就定义了整个生态的物理法则**。今天大部分关于 AI 银行的讨论还停留在"用 AI 提升体验",但真正的战略战场是更底层的——Agent 之间用什么"语言"谈金融?

让我把这件事拆开,试着画出一张正在形成的地图。

## 一、为什么协议层会成为兵家必争之地

先理解协议的本质。

协议不是技术规范那么简单,它是**多方协作的契约**。当一个协议被广泛采用,它会产生几个深远的后果:

**后果一:协议定义了什么是"可能的"**。比如 HTTP 定义了 Web 上能做什么、不能做什么。Agent 时代的金融协议会定义"Agent 之间能完成什么样的金融交互"——是只能查询余额,还是能发起授权交易,还是能进行复杂的金融决策协商?

**后果二:协议决定了价值在哪里沉淀**。TCP/IP 是开放协议,导致互联网的价值沉淀在应用层(Google、Facebook);App Store 是封闭协议,价值沉淀在平台层(苹果抽成 30%)。金融 Agent 协议如果是开放的,银行有机会保住价值;如果被某个平台垄断(比如 OpenAI 或 Apple 定义了金融 Agent 的事实标准),银行就变成了 App Store 里的一个 App。

**后果三:协议是事实上的监管入口**。监管者不可能直接监管每一个 Agent,但可以通过监管协议——要求所有金融交互必须符合某个协议,在协议层嵌入合规规则——来实现规模化监管。这意味着**协议制定权和监管话语权深度绑定**。

所以协议层的争夺,本质上是在争夺三件事:**可能性边界、价值分配、监管话语权**。

## 二、协议层的多层结构

把"金融 Agent 协议"当成一个单层概念是过于简化的。真实情况是,这是一个**多层协议栈**,每一层解决不同的问题,每一层都有自己的标准之争。

让我尝试画出这个栈,从底层往上:

**第一层:Agent 通信协议层**。Agent 之间怎么互相发现、握手、交换消息?这是最底层的"管道"。今天的代表是 Anthropic 推动的 MCP (Model Context Protocol)、Google 提出的 A2A (Agent-to-Agent),以及一些更早的尝试。这一层目前还在标准化早期。

**第二层:身份与授权层**。Agent 怎么证明"我是 X 用户授权的代理人"?授权范围怎么表达?怎么撤销?这一层会演化出 Agent 时代的 OAuth——但比 OAuth 复杂得多,因为它需要支持**有条件、可委托、可撤销、可审计**的授权关系。

**第三层:金融语义层**。这是最有意思也最难的一层。Agent 之间谈金融,需要一套**金融领域的共同语言**。"一笔贷款"在协议里怎么表达?利率结构、抵押条件、提前还款规则、违约条款——这些必须是机器可读、语义无歧义的。今天人类世界用合同(自然语言 + 法律解释)来处理这些,Agent 世界需要某种**结构化的金融合约语言**。

**第四层:交易与结算层**。Agent 之间达成的金融决策,怎么落地成真实的资金流动?这一层连接的是传统的清算结算体系(SWIFT、各国 RTGS、卡组织)或者新兴的链上结算(稳定币、CBDC)。

**第五层:合规与审计层**。每一笔 Agent 间的金融交互,怎么留下可被监管审查的痕迹?KYC/AML 怎么在 Agent 世界落地?这一层是监管直接介入的地方。

这五层不一定都有"显性的协议",但每一层都有协议化的需求。**整个金融 Agent 生态的健康程度,取决于这五层是否都有足够好、足够开放的协议**。

## 三、当前各方在协议层的位置

把目光投向现实,看看今天各方实际上在做什么。我会做一些判断性的描述,但需要提醒:这个领域变化极快,几个月就可能洗牌。

**AI 平台方(Anthropic、OpenAI、Google)**

他们的优势在第一层(Agent 通信)和第二层(身份授权)。MCP 是 Anthropic 提出的,目标是定义 Agent 怎么调用外部工具——这是一个非常底层、非常通用的协议,但它把"外部工具"作为被调用者的角色锚定了。如果金融服务被认为是 MCP 协议下的一种"工具",那银行就被定义为工具提供方,而 AI 平台是协调者。

这是一个微妙但关键的位置之争。**被定义为"工具"的人,在生态里是被调用的,不是主导的**。

**支付/卡组织(Visa、Mastercard、PayPal、Stripe)**

他们最积极。Visa 和 Mastercard 都已经推出了面向 Agent 的支付协议(Visa Intelligent Commerce、Mastercard Agent Pay 等类似产品),核心是要在 Agent 时代继续保住"支付路由"的位置。Stripe 在更早就推出了面向 AI Agent 的 API。

这些玩家的战略逻辑很清晰:**我已经是今天的支付协议主导者,我必须在 Agent 时代延续这个位置,否则会被新协议淘汰**。

**银行**

普遍滞后。少数大行(摩根大通、花旗、汇丰、招商、平安等)开始有动作,但大部分还在思考阶段。这其中有几个结构性原因:

- 银行的核心系统老旧,API 化都没完成,更别说 Agent 化
- 银行的监管约束让它对新协议天然谨慎
- 银行的组织结构不擅长做平台型基础设施

这导致一个可能的、令人担忧的后果:**当 Agent 时代真正到来,金融协议的主导权可能不在银行手里,而在 AI 平台和支付组织手里**。

**监管机构**

监管的速度天然比技术慢,但在协议层有独特的杠杆。欧盟的 PSD2/PSD3 已经在 Open Banking 协议上有过尝试,未来可能扩展到 Agent。新加坡、英国、香港等金融科技友好的监管沙盒在探索 Agent 金融规则。中国的监管在数据安全和算法治理上有比较强的立场,可能会形成自己的协议路径。

监管在协议层的策略,会深刻影响这个生态长成什么样。

**链上世界**

这是一股不容忽视的力量。区块链原生的金融协议(DeFi 协议、智能合约、稳定币)在某种意义上是"天生 Agent 友好的"——它们本来就是程序化、无须信任中介的金融交互。如果 Agent 时代到来,链上世界很可能成为 Agent 间金融协议的一个重要试验田或竞争路径。

这里的张力是:链上世界绕过了银行和监管,效率高但合规弱;银行体系合规强但 Agent 化慢。**最终的协议演化,可能是两者的某种融合**——比如合规化的稳定币 + 链上结算 + 链下 KYC。

## 四、协议演化的几条可能路径

把上面的力量综合起来,我能看到几条可能的演化路径。这些不是预测,而是几种可能的"未来形态",真实演化大概率是这些路径的混合。

**路径一:AI 平台主导的协议(Agent-centric)**

OpenAI、Anthropic、Google 等通过通用 Agent 协议(MCP 及其后继者)定义了 Agent 间交互的基础层。金融服务被纳入这个框架,作为可被调用的工具能力。在这个路径下,**银行是被调用方**,价值很大程度上转移到 AI 平台和拥有最强金融 Agent 的玩家手里。

类比:这有点像今天 App 在 iOS/Android 平台上的关系。银行的体量再大,也是在别人定义的协议里玩。

**路径二:支付组织延伸的协议(Payment-centric)**

Visa、Mastercard、Stripe 等基于现有的支付协议,延伸出 Agent 支付协议。这个协议从"支付"扩展到"金融服务调用",银行通过既有的卡组织关系参与。这条路径对银行相对友好,因为银行和卡组织有长期合作关系,但卡组织会拿走更多价值。

类比:类似当年银行从直连模式被卡组织"中介化"的历史在 Agent 时代重演。

**路径三:银行联盟/行业标准主导(Bank-centric)**

由几家头部银行联合行业组织(SWIFT、ISO、各国银行业协会)推动一个开放的、银行友好的 Agent 金融协议。这条路径要求银行有足够的紧迫感和合作意愿,历史上银行业的合作记录是参差的(SWIFT 算成功,Libra 失败)。

类比:类似 Open Banking 的演化,但更进一步。

**路径四:监管驱动的协议(Regulator-centric)**

监管机构定义 Agent 金融交互的强制协议,所有玩家必须遵守。这条路径在欧盟、新加坡、中国等监管主导型市场可能性较高。优点是合规清晰、用户保护强;缺点是创新被抑制,且不同司法管辖区的协议可能割裂。

类比:类似欧盟的 GDPR 和 PSD2 对全球的影响。

**路径五:链上协议成为事实标准(Crypto-native)**

链上稳定币、智能合约、DeFi 协议演化成熟,成为 Agent 间金融交互的主要协议层。传统银行要么接入这个体系,要么被绕过。

类比:类似互联网早期 TCP/IP 战胜各种私有网络协议的过程。

**最可能的现实:多协议并存且互通**

实际上,我判断未来 5-10 年大概率是上述多条路径并行演化,形成一个**多协议、多层次、有互通桥梁的复杂生态**。不同场景、不同地域、不同用户群,会用不同的协议组合。

这意味着,银行真正需要的能力是**协议中立性 + 协议互通能力**——不押注任何单一协议,但在所有主流协议上都能提供服务,并能在协议之间做翻译和路由。

## 五、协议层的核心设计问题

不论最终是哪条路径,有几个设计问题是绕不开的,值得拿出来单独讨论。

### 问题一:授权的颗粒度和可组合性

Agent 时代的金融授权,不能是 OAuth 那种粗粒度的"全部访问 / 全部不访问"。它必须支持:

- **金额维度**:授权 X 元以下的交易,超过需要人工确认
- **场景维度**:授权用于购房相关的金融决策,不能用于股票投资
- **时间维度**:授权有效期 30 天,过期自动失效
- **对手方维度**:授权只能与特定的对手方 Agent 交互
- **可委托性**:用户授权银行 Agent,银行 Agent 能否再授权下游 Agent?如果能,怎么追责?

这个授权模型的设计,会直接影响协议的复杂度和可用性。设计得太松,用户失去控制;设计得太紧,Agent 寸步难行。

### 问题二:意图的表达和协商

Agent 之间不只是调用 API,它们要协商。比如:

- 购房 Agent:"用户需要 100 万房贷"
- 银行 Agent:"可以提供,利率 4.5%"
- 购房 Agent:"另一家报价 4.3%"
- 银行 Agent:"如果用户把工资代发也转过来,我可以做到 4.25%"

这种协商在人类世界里靠对话完成,在 Agent 世界里需要一套**结构化的协商协议**——既要表达请求和报价,也要表达条件和让步空间。

今天还没有成熟的协议在这一层,但这是 Agent 时代金融效率提升的最大空间。**谁定义了金融协商协议,谁就定义了 Agent 时代的"谈判桌"**。

### 问题三:身份的可验证性

银行 Agent 怎么知道对面那个声称代表用户的 Agent 真的是用户授权的?用户怎么知道一个号称"银行 Agent"的对话方真的是银行?

这需要一套**Agent 身份验证体系**,可能基于:

- 中心化的 Agent 注册和认证机制(类似 SSL 证书)
- 去中心化的可验证凭证(W3C DIDs 等)
- 平台级的身份认证(由 AI 平台担保)

不同方案对应不同的信任根。这个选择会影响整个生态的开放性。

### 问题四:合约的可执行性

Agent 间达成的金融协议,法律效力如何?

如果一个用户的个人 Agent 和银行 Agent "谈定"了一笔贷款,这构成法律意义上的合同吗?如果其中一方违约,怎么追责?这是法律和协议交叉的灰色地带。

可能的路径:

- 把 Agent 间的协议视为"要约/承诺",最终需要人类确认才生效(保守路径)
- 用户预先授权 Agent 在某些范围内的决策具有法律效力(中间路径)
- 通过智能合约让协议自动执行,绕过传统法律框架(激进路径)

不同路径对应不同的效率和风险权衡。

### 问题五:监管的嵌入点

监管不可能监管每一个 Agent,但可以在协议层嵌入合规规则。比如:

- 协议规定每一笔 Agent 间金融交互必须包含 KYC 证明
- 协议规定大额交易必须留下可审计的链路
- 协议规定特定类型的金融产品(比如高风险衍生品)不能被 Agent 自主决策

这种**协议级合规**是 Agent 时代监管的核心机制。但它需要监管机构有足够的技术理解和制定标准的能力——这是个能力建设挑战。

## 六、对银行的战略含义

把上面的分析收敛到银行视角,有几个判断我觉得比较重要。

**判断一:银行不能等协议标准化再行动**

历史上银行习惯等行业标准成熟再跟进,但在 Agent 协议层,等待意味着被边缘化。协议是被建构出来的,谁早期参与谁有定义权。**银行至少要在主流协议提案中有发言权**,不论是通过行业组织(SWIFT、ISO)、监管沟通,还是直接与 AI 平台合作。

**判断二:银行需要"多协议适配能力"作为核心基础设施**

不要押注单一协议,而是构建一个**协议适配层**——把内部的金融能力,以适配多种外部协议的方式暴露出去。无论最终主流协议是 MCP 系、卡组织系、Open Banking 系还是链上系,银行都能接入。这个适配层本身就是银行在 Agent 时代的核心竞争力之一。

**判断三:在金融语义层(第三层),银行有独特的主导可能**

回到协议栈五层,银行在第一层(通信)、第二层(身份)、第四层(结算)、第五层(合规)都不一定有主导优势——这些层有更强的玩家或更专业的机构。

但**第三层金融语义层,银行是最有能力主导的**。因为金融产品的复杂性、合约的精确表达、风险结构的标准化——这些是银行的核心专业能力。如果银行能在这一层联合起来,定义一套被广泛采用的"金融合约表达语言",它在整个协议栈里就有了不可替代的位置。

这是一个被低估的战略机会。

**判断四:监管层面的话语权至关重要**

银行天然和监管有深度沟通,这是 AI 平台和科技公司不具备的优势。在协议层涉及监管嵌入的部分,银行应该主动和监管合作,推动**对银行业有利、对用户有保护、对创新有空间**的协议规则。

如果银行在这件事上缺席,监管规则可能由其他更激进的玩家影响形成,最终银行被动适应。

**判断五:协议中立性是终极防线**

如果银行在协议制定上完全失败,最后的防线是**保持协议中立**——不被任何单一协议平台绑定。这意味着对任何 AI 平台、任何卡组织、任何链上协议都开放接入,但不深度依赖任何一个。

这是一个保守但稳健的策略。它牺牲了主导权,但保住了生存权。

## 七、一个核心判断

如果让我对整个协议层做一个核心判断,我会说:

> **Agent 时代金融协议层的真正赢家,不是技术最强或体量最大的玩家,而是最早理解"协议即权力"并采取行动的玩家。**

今天 AI 平台和支付组织已经开始行动了。银行如果不在未来 2-3 年内进入这场协议博弈,等到生态格局确定再想加入,基本就是 App Store 里的一个 App 的命运。

而且,这个协议层一旦定型,**它的网络效应和路径依赖会让后来者极难撼动**。就像今天没人能再做一个新的 TCP/IP,Agent 时代的金融协议一旦确立,银行就只能在既定规则里玩。

所以这是一个**时间窗口非常有限的战略问题**。它不是一个技术问题,不是一个产品问题,而是一个**生态位的争夺问题**。意识到这件事的紧迫性,可能比讨论具体协议方案更重要。
