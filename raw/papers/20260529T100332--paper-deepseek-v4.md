# 问题

模型现在越来越像一个加班的人：脑子够用，但桌面太小。资料一多，纸摊不开；推理一长，草稿放不下。

这篇 DeepSeek-V4 解决的不是「模型还能不能更聪明」这个泛问题，而是一个更硬的限制：如果未来的模型要做长时间 agent、跨很多文档分析、长链路推理，它必须能把百万 token 放进工作台里，还不能每看一眼都烧掉巨大算力。

传统 attention 的问题很直白。上下文越长，每个新 token 越要回看前面一大片内容。长度涨到百万级，KV cache 和计算量就会变成墙。DeepSeek-V4 的路线是：不再让模型逐字回看全部历史，而是把历史压成多种粒度的索引、摘要和局部窗口。模型看远处时看压缩地图，看近处时看原始细节。

# 翻译

这篇论文的中心画面是一张可以缩放的地图。

以前的长上下文模型像把整座城市的每一块砖都铺在桌上。信息完整，但桌子爆了。DeepSeek-V4 换了做法：远处街区用地图块，近处路口保留高清照片。需要找东西时，先用索引挑出可能相关的地图块，再细看。

它主要做了四件事。

第一，做了两个模型：

- DeepSeek-V4-Pro：总参数 1.6T，每 token 激活 49B。
- DeepSeek-V4-Flash：总参数 284B，每 token 激活 13B。

两者都是 MoE。Pro 像大仓库，Flash 像更便宜的快递站。每次只激活一小部分专家。

第二，把 attention 改成 CSA 和 HCA 混合。

CSA 是「压缩后再挑」。它先把每 4 个 token 的 KV 压成一个条目，再用一个轻量索引器选 top-k 条目。Pro 的 top-k 是 1024，Flash 是 512。这样模型不用看所有历史，只看被索引器认为相关的压缩块。

HCA 是「更狠地压缩」。它把每 128 个 token 压成一个条目，然后做更便宜的 dense attention。它不追求精细找针，主要负责让模型对很远的历史仍有一个粗视野。

再加一个 128 token 的滑动窗口。近处不压缩，保留细节。

可以这样看：

    near tokens  -> raw window        -> see exact words
    mid history  -> CSA compressed    -> select useful blocks
    far history  -> HCA compressed    -> keep broad memory

第三，它用了 mHC，把残差连接从「简单相加」升级成「有约束的混合」。普通 Transformer 的每层像把新结果倒回同一个桶里。mHC 更像在几个通道之间做稳定调配，让深层网络的信息流不那么乱。论文说这能增强建模能力，但也承认实现复杂，未来要再简化。

第四，它把 Muon optimizer 引入大规模训练。Muon 不是这篇论文原创，但 DeepSeek 把它工程化到了 trillion MoE 训练里。多数参数用 Muon，embedding、prediction head、RMSNorm 等仍用 AdamW。目标是收敛更快，训练更稳。

训练规模也很重：

- Flash 预训练 32T tokens。
- Pro 预训练 33T tokens。
- 训练长度从 4K 逐步拉到 16K、64K、1M。
- 先 dense attention 热身，再引入 sparse attention。

它还暴露了两个训练补丁。

Anticipatory Routing：路由不要用当前模型即时算，而是用历史参数提前算好。直觉是 MoE 路由和 backbone 同步乱跳时容易把 loss spike 放大。把路由延迟一点，像给系统加阻尼。

SwiGLU Clamping：把 SwiGLU 的异常值夹住。linear 分量限制在 [-10, 10]，gate 分量上限 10。这个办法朴素，但他们说很有效。

效果上，论文最想卖的不是单榜第一，而是「百万上下文更便宜」：

- 1M 上下文下，V4-Pro 的单 token 推理 FLOPs 约为 V3.2 的 27%。
- 1M 上下文下，V4-Pro 的 KV cache 约为 V3.2 的 10%。
- V4-Flash 更激进，FLOPs 约为 10%，KV cache 约为 7%。

能力上，Pro-Max 在不少开放模型对比里领先。论文声称：

- SimpleQA-Verified：57.9，低于 Gemini-3.1-Pro 的 75.6，但高于 K2.6、GLM-5.1。
- HLE：37.7，低于 Gemini-3.1-Pro 的 44.4、Opus-4.6 的 40.0、GPT-5.4 的 39.8。
- Codeforces rating：3206，高于 GPT-5.4 的 3168 和 Gemini-3.1-Pro 的 3052。
- Terminal Bench 2.0：67.9，低于 GPT-5.4 的 75.1，略低于 Gemini-3.1-Pro 的 68.5。
- SWE Verified：80.6，和 Gemini-3.1-Pro 接近，略低于 Opus-4.6 的 80.8。

所以它不是全面压过闭源前沿模型。更准确的说法是：开放模型在长上下文效率、代码竞赛、中文写作和部分 agent 任务上追得很近；在知识密度和复杂指令上仍有短板。

# 核心概念

## 1. CSA

一句话：CSA 是先把历史压成块，再从块里挑重点看。

类比：你读一本厚书，不是一页页翻，而是先看目录和索引，找出相关章节，再回去读那些章节的摘要版。

为什么重要：没有 CSA，百万上下文里每个 token 都要面对太多历史。CSA 让模型从「全看」变成「先找再看」。

## 2. HCA

一句话：HCA 是把更远的历史压得更狠，只保留粗轮廓。

类比：开车导航时，市区内要看车道线，跨省时只看高速和城市名。远处不需要每个路牌都高清。

为什么重要：CSA 还要做 top-k 选择，适合中远距离的相关信息；HCA 更便宜，适合让模型始终知道远处大概发生过什么。

## 3. Test-time scaling 的上下文地基

一句话：推理时多想几步，会吃掉更多 token；如果上下文贵，多想就不经济。

类比：一个人做复杂题时需要草稿纸。草稿纸太小，他不是不会做，而是中途只能擦掉前面的推导。

为什么重要：这篇论文把长上下文和推理能力绑在一起看。百万上下文不是为了塞更多网页，而是为了让 agent 和 reasoning 在更长时间里不断积累中间状态。

# 洞见

长上下文的关键不是「记住更多字」，而是给模型一套能缩放的工作台：近处要高清，远处要地图，中间要索引。

这个想法可以脱离论文使用。做 agent 记忆、项目知识库、个人 AI 工作流时，也不该把所有材料平铺给模型。应该按距离和任务相关性分层：当前窗口保细节，近期工作保摘要，长期记忆保索引和可追溯链接。

# 博导审稿

选题眼光很好。这是真缺口。百万上下文不是营销数字，背后是 test-time scaling、长任务 agent、跨文档分析和在线学习的共同瓶颈。

方法成熟度高，但不优雅。CSA、HCA、mHC、Muon、FP4、KV cache 分层、on-disk cache、Anticipatory Routing、SwiGLU Clamping 全都堆上了。它像一台能跑的工程机器，不像一个已经被压缩到最小公理的架构。

实验有诚意，但有两类数字要谨慎。公开 benchmark 覆盖很广，和开源、闭源模型都比了，这是优点。内部中文写作、白领任务、代码 agent 评测很有参考价值，但可复现性弱，尤其是人评标准、任务采样、agent harness 细节不透明。

写作功力中上。它把系统工程说得比较全，也诚实承认架构复杂、训练稳定性原理没完全搞懂。但关键设计的消融不够让人放心。比如 CSA/HCA 各自贡献、mHC 独立收益、Muon 和数据质量之间的贡献拆分，还可以更硬。

判决：weak accept。理由是问题重要、工程完成度高、开放模型有明显推进；但方法太复杂，部分 claim 依赖内部评测和系统实现，科学解释还没完全跟上。

# 启发

迁移：你的 AI 认知框架可以把「上下文」从一个窗口，升级成一套分层工作台。

具体做法：

- 当前任务：保留原文、最新状态、关键约束。
- 近期项目：保留结构化摘要、决策、风险、下一步。
- 长期框架：保留概念索引、链接、反复出现的问题。

这和你的 Memory V3 很贴。NOW.md、daily、MEMORY.md、Obsidian 不是简单分目录，而是在模拟 CSA/HCA：近处详细，远处压缩，关键时可回源。

混搭：这篇论文的 agent 方向可以和你的「一主一审」编码协作结合。主 agent 不需要一直带全量项目历史；它需要一个压缩索引层，能快速找回相关决策、测试失败、已知坑和审查意见。

可以产出一个实践规则：每个长任务都维护三层上下文：

- live context：当前正在改的文件和失败日志。
- task digest：本轮目标、已做变更、未决风险。
- retrieval index：历史设计、规则、相关 issue 的入口。

反转：别再把「更长上下文」当成少做整理的理由。DeepSeek-V4 的方向恰好相反：上下文越长，越需要压缩、索引和分层。粗暴塞全文只能把成本和注意力噪声一起放大。

对你最有用的一句话是：百万上下文不是免整理，而是让整理后的多层记忆有地方展开。
