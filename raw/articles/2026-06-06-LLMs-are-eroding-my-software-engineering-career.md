## 内容归纳

作者是一名有 10 年经验的软件工程师，长期在金融、记账、支付处理等领域做后端开发。他原本相信自己的职业差异化来自三类积累：支付 / 金融领域知识，分布式系统和生产事故调试经验，以及代码质量和软件架构能力。

文章按三根支柱被侵蚀展开：

1. **领域知识被侵蚀**
   作者曾经以 PCI 合规、复式记账、托管、对账、支付生命周期、银行转账幂等等领域经验作为竞争优势。但在公司推动使用 ChatGPT / Claude 写设计文档后，他发现 LLM 能在文档、公开文章和技术材料之间连接知识点，帮助生成支付系统设计和 trade-off 判断。模型仍需要人引导，但它已经能压缩多年经验学习曲线。

2. **调试与分布式系统经验被侵蚀**
   作者一度认为 debug race condition、分布式系统、三方 API 边界问题是人类工程师长期优势。但随着 Claude Code、Codex、MCP、Sentry / Datadog 等观测工具接入 agentic workflow，他看到过去需要一天甚至两天的 bug 被一次性定位和修复。这里真正的信号不是某个模型多强，而是模型和工具链接入后，排障经验被产品化、流程化、可调用化。

3. **代码质量与架构品味开始被降权**
   作者最后保留的信心是重构、DDD、Hexagonal、Clean Architecture、SOLID 等代码组织和架构品味。但他观察到行业可能正在接受更低等级的代码库：只要 agent 能继续维护，代码未必还要保持给人类长期阅读的 A/B 级质量。人仍要防止 F 级不可维护系统，但 C/D 级代码库可能变成可接受状态。

作者最后的焦虑是：他花了十年积累的东西，正在变成“promptable”的通用能力。招聘也从“某领域软件工程师”弱化为“软件工程师”，领域熟悉度不再是强区分项。他还没有找到清晰出路，只能猜测是否要转向模型研究、数学统计，甚至考虑把木工爱好变成职业。

## 可沉淀模型

### 高级工程师护城河迁移模型

过去高级工程师的护城河常被理解为：

- 领域知识：知道业务如何真实运转。
- 排障经验：能在复杂生产环境中定位问题。
- 架构品味：能让系统长期可维护。

LLM + agent + MCP / observability 的组合正在把这些资产逐步“外部化”：

- 领域知识从人脑经验，变成模型可检索、可拼接、可解释的上下文。
- 排障经验从个人直觉，变成日志、trace、Sentry、Datadog、runbook 和 agent workflow 的组合能力。
- 架构品味从个人审美，变成可被组织选择性坚持或放宽的质量策略。

新的职业护城河不再是“我知道什么”，而是：

- 我能否定义正确问题。
- 我能否供给高质量上下文。
- 我能否设计 agent workflow。
- 我能否建立质量门禁和验收标准。
- 我能否把一次成功经验沉淀为组织可继承的资产。
- 我能否对业务结果负责，而不是只对局部代码负责。

### 判断力基线的成人职业版本

教育场景里的判断力基线是：先有自己的问题感、表达和判断，再让 AI 加速。

工程职业场景里的判断力基线是：当代码、文档、debug 都能被 agent 执行时，人还必须能判断：

- AI 的方案是否真的适合当前业务约束。
- 模型是否漏掉合规、风控、安全、长期维护成本。
- 哪些代码必须保持人类可读的 A/B 级，哪些临时工具可以接受 C 级。
- 一次 debug 成功是否应该沉淀为 runbook、测试、监控、trace 或 agent workflow。
- 组织是否真的因此缩短了从问题到结果的闭环。

### 对金融 / 银行 AI 改造的提示

金融领域尤其不能简单接受“代码给 agent 读就行”。在支付、账本、对账、风控、合规、审计等场景，代码质量、人类可解释性和责任链仍可能是强约束。

更合理的策略不是守住旧式“专家亲手做”，也不是放任低质 agent 代码，而是把领域专家经验转译为：

- 领域模型。
- 设计文档模板。
- 质量门禁。
- 回归测试。
- 监控 / trace。
- runbook。
- agent 可调用工具。
- 审计和责任机制。

这样领域专家不是被动等待经验贬值，而是主动把经验变成组织 runtime。
