# AI越强，人越忙：一个住在未来的人说了什么

## 摘要

这篇 X 长文整理了 Lenny 访谈 Every CEO Dan Shipper 的观点。Every 是一个约 30 人、全员重度使用 Codex / Claude Code 等 AI 工具的公司。文章的核心反直觉判断是：AI 越强，人不一定越闲，反而会创造新的工作，尤其是定义问题、管理 Agent、维护工作流、验收质量和把真实经验固化为组织系统。

几个关键观点：

- AI 编程模型能解决被定义清楚的问题，但还不擅长主动判断“这个问题应该被重新定义”。Dan 的“高级工程师基准测试”显示，烂代码库场景里，人类高级工程师会主动推倒重来，而多数模型只会沿着“修 bug”的字面任务推进。
- “每个 Agent 背后都需要一个人”。Agent 不是装上就自然产生价值，它会坏、会偏离、需要权限、上下文、维护和质量检查。现实路径可能先是公司级通用 Agent，由专人维护，再逐步下沉到团队和个人。
- Codex / Claude Code 可能成为新的工作操作系统。过去是把 AI 嵌进 SaaS，未来可能是把 SaaS 放进 Agent 里运行。
- CLI 的短期优势不在 CLI 本身，而在本地权限完整、终端文档丰富、模型训练充分。长期主战场可能回到更适合人机协作的 GUI / 工作台。
- Agent 不一定摧毁 SaaS，可能成为 SaaS 的新用户。SaaS 的重点从“内置 AI 功能”转向“对人和 Agent 都友好”。
- PM、设计师、业务 owner 的价值可能上升：当模型足够能实现，真正稀缺的是产品判断、审美、交互感、上下文组织和结果 owner。
- Dan 不认为大规模失业会立刻发生，但强调不能躺平。最好的策略不是刷观点，而是把新模型用在自己真正头疼的真实任务上。

- 对应活问题：
  - Q1：通用智能体何时真正接管白领工作流？
  - Q4：AI 原生组织到底长什么样？

- 有用之处：这不是模型发布新闻，而是一个 AI 重度使用组织的 operator signal。它把“Agent 需要 owner”“AI 增强后验证和协调更贵”“真实工作流小实验比观点争论重要”等已有判断，落到了 Every 的具体组织样本上。
- 框架贡献：
  - L1：补充“问题重定义”是当前 Agent 能力边界之一。模型可在明确任务上变强，但高级工程师式的“看见问题定义错了，并拒绝局部修补”仍是关键门槛。

## 正文整理

著名 PM 人 Lenny 访谈了 Every 公司的 CEO Dan Shipper。文章认为 Dan 的很多观点犀利且反共识，因为 Every 不是在预测未来，而是在真实工作中重度使用 AI。

Every 是一家约 30 人的公司，工程师、编辑、销售、客服都在用最新 AI 工具干活。按理说，这种公司应该越来越精简，但过去一年员工人数反而翻了一倍。

Dan 提出一个悖论：AI 越强，人反而越忙。原因不是自动化失败，而是自动化创造了新的工作：管理自动化本身。

Dan 做过一个“高级工程师基准测试”。他用 vibe coding 做了写作工具 Proof，上线第二天服务器每隔 10 分钟就崩一次。他让 Codex 修，Codex 说修好了，但又冒出四个新 bug，循环往复。后来他请两位真正的高级工程师独立重写代码库，于是有了这个基准：让 AI 接手同一个烂摊子，从头重写。

结果是，几乎所有模型得分在 30 分左右，人类高级工程师能到 85 到 90 分。GPT-5.5 是异类，跳到 62 分，而且它是唯一一个敢推倒重来的模型。其他模型接到“修 bug”的指令，就真的一个一个修 bug。

人类高级工程师会先扫一眼代码库，然后判断“这东西应该重写”。关键不只是修复，而是发现原问题定义错了。模型能解决定义清楚的问题，但“发现这个问题需要被重新定义”仍是弱项。benchmark 只能测量人类已经想清楚、能打分的那部分工作，剩下那部分需要先想到要问什么。

这也是 Every 人越招越多的原因：每一个 Agent 背后，都需要一个真正关心它在做什么的人。Dan 把这叫做“每个 Agent 都需要一个人”。

Dan 预测，未来一年多数人的工作方式会朝两个方向演化。

第一种是公司共用一个超级 Agent。不是每个人一个私人助理，而是整个公司共用一个挂在 Slack 里的 Agent，所有人都能调用。Shopify 和 Ramp 已经有类似实践。Dan 最初也以为每个人都会有个人 Agent，但后来改变看法，因为 Agent 需要人照料。Every 早期很多人设置了自己的 Agent，后来一个个放弃，因为它会坏，需要 SSH 进服务器，需要持续调整。没人关心它在做什么时，它就会悄悄变得没用。

所以现实路径可能是：先有公司级通用 Agent，由专人维护；随着模型更可靠，再逐渐分裂出团队级、个人级 Agent。这个专门维护 Agent 的人，Dan 称为“前沿部署工程师”（Forward Deployed Engineer）。Every 内部已经有这样的岗位。

第二种是 Codex 或 Claude Code 成为新的工作操作系统。Dan 现在处理邮件时，会让 Codex 打开内置浏览器，把所有邮件聚合到一个页面，然后对着屏幕说话。例如让它把过去四年的文件整理成报告发给律师。写文章时，他在 Codex 内置浏览器里打开 Proof，Codex 能看到他在写什么，他也能看到 Codex 在做什么，两者实时协作。招人时，他让 Codex 找到特定背景的人，然后回来发现 Codex 找到并在 Twitter 上关注了目标对象。

文章的判断是：过去我们把 AI 嵌进 SaaS 工具，未来可能是把 SaaS 工具放进 AI Agent 里跑。用户在 Codex 里使用 Proof，用的是自己的 token，而不是 Proof 产品的 token。SaaS 厂商不一定需要烧钱堆 AI 功能，而是需要让产品对人和 Agent 都友好。

Dan 还认为，CLI 的时代已经被快速穿过。Claude Code 火起来时，很多人以为是终端命令行的魔力让它好用。Dan 认为真正原因不是 CLI 本身，而是 Agent 在本地机器上有完整访问权限，以及网上有大量终端使用内容可供模型学习。GUI 本来就是为了让人更舒服而发明的，这个逻辑并没有改变。

关于 SaaS，Dan 的观察也偏反共识。很多人认为 Agent 会让人绕过 SaaS，但他认为 Agent 不会替代 SaaS 用户，而会成为 SaaS 新用户。Every 内部人人都用 Codex 和 Claude Code，但 SaaS 支出比去年更高，因为 Agent 在高频使用 SaaS。

Every 的 Proof 是开源的。用户遇到问题时，不再只是给客服发邮件，而是让自己的 Agent 发一份 bug 报告，里面有精确复现步骤和代码库分析，直接变成 GitHub issue，然后 Every 的 Agent 去修。这个闭环比传统人工客服流程快。

对 SaaS 公司来说，重点不是把 AI 塞进自己的产品，而是让产品同时对人和 Agent 友好，让两者在同一界面上协作，并能互相看到对方在做什么。

Dan 对 PM 和设计师这两个角色很看好。PM 出身的人如果学会 Cursor，产品感和用户洞察配上足够好的编程模型，会成为很强的组合。他不需要组织一个完整团队来实现想法，可以直接做。设计师同理，以前想到交互要等工程师实现，现在可以自己发 PR。当所有人都用 vibe coding 批量生产相似界面时，真正懂审美和交互的人反而更值钱。

Dan 判断大规模失业不会马上发生。很多被归因于 AI 的裁员，其实是过度招聘的修正，AI 只是方便的借口。但这不意味着可以躺平。他的建议是“骑上模型”：不是因为 FOMO，而是因为好奇。每次有新模型出来，把它用到你真正在乎的事情上。哪怕上次试过不行，这次也再试一次。

他认为 AI 的真正前沿不只在旧金山，而在每一个把 AI 用在真实工作场景的人那里。硅谷的人在造 AI，但不一定知道怎么用好它。每次新模型出来，真实用户都可能是最早发现它能做什么的人之一。

最后的建议是：别争论 AI 会不会改变世界，找一件真正头疼的事，试着用 AI 解决它。当第一次感受到“这也行？”时，就不需要别人再说服你了。
